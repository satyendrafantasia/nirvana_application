# Nirvana Wellness pre-deployment security review

Review date **28 November 2026**. The fixes were developed and tested on `review/predeployment-security-20261128` from GitHub `main` at `d3f08954dffdbdbce18956590c9163065798bcee`. Production observations below cover only the public web assets.

The application uses Spring Security with database-backed users, roles and spa memberships. The browser uses a short-lived access token and a rotating refresh credential. MariaDB/MySQL stores booking commitments and payment state. Razorpay supplies payment evidence. Spa owners publish media through private S3 uploads. Local tests use synthetic principals, a disposable MariaDB database and controlled provider responses. Production inspection was limited to publicly served frontend files.

## Dependency disposition

Neither XSLT views nor server-sent view fragments were found in the application source. Both vendor advisories still flag the installed Spring MVC version. Spring lists a 6.2.20 enterprise fix and an open-source fix beginning at 7.0.9. Obtain a supported patched 6.2 release or schedule a Spring Boot 4 / Framework 7 migration and regression test. Record the deployment decision if retaining 6.2.19 on the strength of the inapplicable feature conditions. [Spring XSLT advisory](https://spring.io/security/cve-2026-47884/) · [Spring fragment streaming advisory](https://spring.io/security/cve-2026-47890/) · [OSV version query](https://google.github.io/osv.dev/post-v1-querybatch/)

## Reproducing the evidence

Use Java 17, a fresh disposable MariaDB schema, test-only credentials and `SCHEDULING_ENABLED=false` for `./mvnw clean verify`. For the frontend use Node 24 and run `npm ci`, `npm run lint`, `npm test`, `npm run build` and `npm run test:browser`. Run `python scripts/check-public-bundle.py frontend/dist` from the repository root. Recheck advisories using `npm audit` and the exact coordinates from `./mvnw dependency:list`. Dependency scans are dated observations.

## Executed verification

| Check | Observed result |
|---|---|
| Java backend and Flyway | Maven clean verify succeeded against a fresh MariaDB schema. 379 passed, zero failed and one optional spa-lead import test was skipped because it requires a separately supplied export. Flyway applied the migrations including V84 and V85. |
| Web client | 200 tests passed across 41 Vitest files. Lint and the production build passed. |
| Browser regressions | 33 Playwright checks passed across Chromium, Firefox and WebKit. These exercise the web interface with test fixtures. |
| Candidate and public assets | Scanned 92 files in the candidate build and 52 linked public JavaScript chunks on `nirvana-spa.in`. No tested private credential signatures or source-map references were found. The public entry map returned HTTP 404. |
| Dependencies | npm reported zero advisories after the upgrades. OSV flagged two advisories on one of 251 resolved Maven components. |

Each owner created a room, therapist, roster and slot at their own spa. Each could read and cancel their own fixture booking. The tests also attempted to access another spa's export and substitute its booking, room, therapist and slot IDs. The requests received 403 or 404, and database assertions checked the other spa's booking status, room, roster and capacity. Each customer could read their own cancellation quote. The other customer's private quote and cancellation were denied.

In the webhook integration test, the Razorpay network client supplied a controlled capture response. A bad signature returned HTTP 400 and left the stored booking pending, payment unpaid, and receipt and alert counts at zero. Two identical signed deliveries returned HTTP 200, left one captured payment on the confirmed booking, and produced one webhook receipt and one customer-email confirmation job. No provider payment or customer communication was sent.

## Unresolved release blockers

1. Rotate the previously disclosed live Razorpay key pair and replace the disclosed Google Places server key with an API-restricted key scoped to the intended server. Configure the matching live webhook secret and delivery events, and rehearse replay and refund handling in Razorpay Test Mode. Use a staged traffic switch to preserve the currently working live checkout.
2. Back up the database, rehearse V84 and V85 with the release migration role, check least-privilege runtime grants, and confirm the privileged-user enrollment/recovery process before enforcing the new sessions.
3. Verify S3 Block Public Access, bucket ownership, approved-origin upload CORS, scoped IAM, expiry of unpublished staging objects, and real upload/download behavior in a staging bucket. Verify exact HTTPS session origin, proxy trust and device behavior alongside the matching frontend and backend.
4. Resolve or explicitly disposition both Spring MVC advisories. Verify production log/trace redaction, access and retention at the reverse proxy and collectors. This source review did not inspect private production logs or send real payments, SMS or emails.
